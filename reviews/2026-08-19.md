**Source:** @millee.md, https://www.instagram.com/p/Db9aX8rhfhU/
**Claim (transcript, ~approximate — Whisper base.en):** "Hide API key… use public
database key, enable R\[L\]S, encrypt sensitive data, enforce server-side auth,
lock record access, block field tampering, secure session cookies, hash
passwords, rate limit login, add bot protection, parameterize queries, validate
all input, escape user content… trim API responses."
**Verified:** Partially. The individual items are standard Supabase/web
practice and correct; the post is a list, not a demonstration.
**Why it fits:** Your global rules have a `## Secrets` section, but it only
covers *never committing* a live key. Grep confirms **no RLS, auth, or
rate-limit guidance anywhere in CLAUDE.md** — and you ship Supabase apps with
Clerk auth where an internal project note already flags account-isolation as an
"ALWAYS check" trap. This is the one genuine gap the whole folder surfaced.

**Proposed diff:**
```diff
 ## Secrets

 Never write a live key, token, connection string, or password into a tracked
 file. Use `process.env.X` with an explicit missing-value throw. If you need a
 credential that isn't in the environment, ask — don't inline it "temporarily".
+
+## Supabase / app security
+
+Before shipping anything user-facing, confirm:
+
+- **RLS is on** for every table holding user data — not just the ones you
+  remembered. A table with RLS off and the anon key exposed is public.
+- The client uses the **anon key only**. `service_role` never reaches the
+  browser or a client component.
+- Auth is enforced **server-side** (route handler / server action), not by
+  hiding UI. Check record ownership on write, not just on read.
+- Login and any write endpoint are **rate limited**.
+- User-supplied content is escaped on render; queries are parameterised.
+
+Account isolation is a live trap here — see the existing auth rule.
```
