### 1. Gate every third-party skill install behind NVIDIA SkillSpector — `~/claude-skills/CLAUDE.md`, `skills/saved-intel/SKILL.md`, `src/inventory.py`
**Source:** @liamjohnston.ai, https://www.instagram.com/p/Dc1oIn8CyDW/
**Claim:** "NVIDIA just flagged 1 in 20 Claude skills as straight up malicious … a quarter of the skills out there have a security hole … it's called SkillSpector, point it at any skill and it hands you a risk score out of 100 … plug it into Claude as an MCP." On screen: `skillspector scan ./lead-generation` → score 58/100, HIGH, "DO NOT INSTALL", findings P2 hidden instructions / PE3 credential access / E1 external transmission.
**Verified:** yes — GitHub API: `NVIDIA/SkillSpector`, 17,341 stars, Apache-2.0, created 2026-03-21, pushed 2026-09-15. README confirms 71 patterns / 17 categories, 0–100 score, `uv tool install`, optional `skillspector mcp`, `--no-llm` static mode. The "26.1% of skills contain vulnerabilities" figure is in the README (31,132-skill dataset); the "1 in 20 malicious" figure is the creator's paraphrase and I did not find it verbatim.
**Why it fits:** this repo's whole job is installing skills that were found on Instagram and TikTok. `skills-restore` and `sync` print `git clone … ~/.claude/skills/` commands with no vetting step, and `~/.claude/hooks/` has nothing equivalent (`secret-guard.js` guards outbound secrets, not inbound skills). One scan per install is cheap and closes the exact gap this pipeline opens. Static mode needs no API key.
**Proposed diff:**
```diff
--- ~/claude-skills/CLAUDE.md
@@ ## Analysing posts
+**Scan before you install.** Every skill that reaches `reports/skills.json` gets
+`skillspector scan <path-or-repo-url> --no-llm` before its install command is run,
+and the score goes in the `verified` field. Anything rated HIGH or "DO NOT INSTALL"
+is rejected in the report, not installed with a caveat.
--- skills/saved-intel/SKILL.md
@@ ### Also write `reports/skills.json`
+Before listing a skill as installable, run
+`skillspector scan https://github.com/<repo> --no-llm --format json` and record the
+risk score in `verified`. Do not list anything the scanner marks HIGH.
```
Install (one-off, this machine): `uv tool install 'skillspector[mcp] @ git+https://github.com/NVIDIA/skillspector.git'`. Record in `skills/provenance.json` at install time.

### 4. Two lines for the pre-ship auth checklist — `~/.claude/CLAUDE.md`
**Source:** @joinbuildingwithai, https://www.instagram.com/p/Dc1cp4MhvKm/
**Claim:** Five Supabase/Next.js login gaps: (1) service-role key in the frontend bundle, (2) user id read from the request instead of the session, (3) RLS off, (4) "your sign out button just deletes the cookie, the session is still live on the server", (5) "'no user found' versus 'wrong password' is a free user list. Use one message for both."
**Verified:** partially — (1)–(3) are standard Supabase guidance and already in your CLAUDE.md. (4) and (5) are correct general practice (server-side `signOut` revokes the refresh token; uniform auth errors prevent account enumeration). No tool to verify, just a checklist.
**Why it fits:** your "Before shipping anything user-facing" block already has RLS, anon-key-only, server-side auth, rate limiting, escaping. Items 4 and 5 are the two it lacks and both bit an internal platform's account-isolation work before.
**Proposed diff:**
```diff
--- ~/.claude/CLAUDE.md
@@ ### Before shipping anything user-facing
 - Login and write endpoints are **rate limited**.
+- Sign-out hits the **server** (`supabase.auth.signOut()` in a route handler / server action), not just a cookie delete.
+- Login returns **one error message** for wrong email and wrong password — no account enumeration.
 - User content escaped on render; queries parameterised.
```
